# 오토바이 phase4 전문가 피드백

| 항목 | 내용 |
|---|---|
| 작성일 | 2026-10-16 |
| 대상 | `docs/오토바이 phase4.md` 기준으로 구현한 앱 (브랜치 `main`, phase4 머지 뒤) |
| 검토 방법 | 요구사항 ID 전수 대조, `npm test`·`tsc`·`oxlint`, 가짜 DB 하네스(`vite.harness.config.ts`)로 진입 → 주간 마감 → 메인 권유 → 편향 보기 → 회고 흐름 실행 |
| 형식 | 기획·디자인·프론트엔드 세 사람이 각자 20년차 관점으로 쓴 피드백. 마지막에 셋이 합의한 우선순위 |

요약: **기획서의 Must·Should는 회고 알림 하나를 빼고 전부 구현되어 있고 규칙대로 동작한다.** 아래는 "되어 있는가"가 아니라 "제품으로 괜찮은가"에 대한 피드백이다. 심각도는 🔴 다음 배포 전, 🟡 다음 버전, 🟢 여유 있을 때.

## 1. 기획 — 20년차 프로덕트 매니저

### 총평

요구사항 ID를 코드 주석까지 끌고 간 추적성은 드물게 좋다. 미정 사항 17개를 "임시 처리대로 구현"으로 닫은 것도 맞는 선택이다. 다만 **"성공으로 본다"고 적어 둔 지표 두 개(NU-8, WC-11)를 볼 방법이 없다.** 저장은 하는데 꺼내 보는 곳이 없으니, 이 버전이 효과가 있었는지 다음 기획 때 말할 수 없다.

### 잘한 것

- 미정 사항을 "결정 → 근거 → 날짜"로 개발 계획에 남겼다(E1~E4). 기획서가 바뀌어도 왜 그렇게 만들었는지 추적된다.
- 권유(4.5)의 범위를 "오늘을 볼 때만, 하나만, 닫으면 그날 끝"으로 좁혀서 잔소리가 되지 않는다.
- 기록 0인 사용자에게도 편향 보기와 권유가 빈 화면이 아니라 "정한 비율"을 보여 준다(BI-6, NU-2). 첫 주 이탈을 막는 디테일이다.

## 2. 디자인 — 20년차 프로덕트 디자이너

### 총평

반말 톤이 끝까지 일관되고, 다크 모드와 safe-area까지 토큰으로 처리한 건 프로토타입을 넘어선 수준이다. 핵심 문제는 **이 앱에서 가장 자주 누르는 것(카테고리 라벨, 요일, 권유)이 가장 작다**는 점이다. 밀도를 높이려다 터치 앱의 기본을 놓쳤다.

### 잘한 것

- `--over`(주황)·`--under`(파랑)로 "더/덜"을 색으로 분리하고, 카테고리 5색은 글자색·바탕색 쌍(`--c0~4`, `--s0~4`)으로 만들어 다크 모드에서도 대비가 유지된다.
- 회고에서 저장 안 한 게 있으면 뒤로 가기 버튼 글자가 "저장 안 하고 나가기"로 바뀐다. 확인 창보다 낫다.
- 빈 상태 문구("할 일을 적어 봐", "모두 끝냈어.", "아직 기록한 시간이 없어. 저녁 회고에서 적어 봐.")가 다음 행동을 알려 준다.
- 편향 보기에서 기록 0이면 실제 막대를 숨기고 정한 비율만 보여 준다. "0% 덜 썼어" 같은 무의미한 판정을 만들지 않았다.

### 한 가지 더

색을 카테고리 **순서**로 정한다(`catStyle`의 `i % 5`). 가운데 카테고리를 지우면 뒤 카테고리들의 색이 한 칸씩 밀린다. 사용자는 "제작은 초록"으로 기억하는데 어느 날 주황이 된다. 색을 카테고리 행에 저장하거나, 지운 카테고리를 포함한 원래 순서로 정하면 된다. 프론트엔드 F10과 같은 항목이다.

## 3. 프론트엔드 — 20년차 프론트엔드 엔지니어

### 총평

의존성이 React와 supabase-js 둘뿐이고, 계산을 `lib/pyramid.ts`로 떼어 `node:test`로 돌리고, 가짜 Supabase로 화면을 띄우는 하네스까지 있다. 이 크기의 앱에 딱 맞는 구조다. 문제는 **쓰기 경로의 원자성**과 **모바일 웹의 기본(뒤로 가기, 로딩 상태)**이다. 둘 다 코드에 "알고 있다"는 주석이 있으니 모르는 게 아니라 미룬 것이다. 이제 갚을 때다.

### 잘한 것

- `Home.tsx`의 `act()`: 화면 먼저 바꾸고 실패하면 서버 값으로 되돌린다. `loaded.ws`로 늦게 온 응답이 다른 주를 덮지 않게 막은 것도 좋다.
- `supabase.fake.ts`: db.ts가 쓰는 체인만 흉내 내는 100줄짜리 가짜. 이것 덕에 Supabase 없이 전 흐름을 돌릴 수 있었다.
- 계산 규칙마다 기획서 ID를 테스트 이름에 적었다(`'편향 경계: … (phase4 BI-4·5)'`). 기획서가 바뀌면 어느 테스트를 고칠지 바로 안다.
- `largestRemainder`가 정수 산술만 써서 부동소수점 동점 문제를 피했다(주석에 근거까지).
- 버튼마다 `aria-label`, 선택 상태는 `aria-pressed`, 상태 메시지는 `role="status"`·`aria-live`. 접근성 기본이 되어 있다.
